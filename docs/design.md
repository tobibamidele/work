# Design decisions and departures from the spec

This implementation follows the specification (`work.md`) throughout. This
document records every place where it differs, extends it, or declines part of
it, with the reason and what was done instead.

## Departures

### 1. `DispatchTx` lives in `work/database`, not in `work`

The spec writes `work.DispatchTx(ctx, tx, ProcessOrder{...})` and also requires
the core package to depend only on Validate (§62: core must not import a
database backend or Lathe). A function in `work` taking a `*lathe.DB` would
break that rule.

**Instead:** `database.DispatchTx(ctx, rt, tx, payload, opts...)` and the safer
`database.WithTx(ctx, db, rt, func(tx *database.Tx) error)`. The core exposes
`Runtime.Prepare` (validate, serialize, build the record) and `Runtime.Enqueued`
(emit the event) so any transactional backend can be built the same way. The
tx handle must be `*lathe.DB` bound to a transaction, matching Lathe's
transaction model; a plain handle is refused (`ErrNotInTransaction`).

### 2. Backend interface refinements

The spec says the interface "should be refined during implementation". Changes,
each with its reason:

- **Explicit `now` on every call.** One `Clock` governs the whole system and
  tests need no sleeping.
- **`Claim` returns `[]*Record` and accepts `Types`.** Batch claiming cuts
  polling queries; the type filter means a worker never burns an attempt on
  work it has no handler for. Still returns `ErrNoWork` when empty.
- **Added `Release`.** Work interrupted by a forced shutdown goes back to the
  queue without losing an attempt; otherwise deploys could exhaust attempts of
  long-running work.
- **Added `FinishCancel`, and `ExtendLease` returns `cancelRequested`.** This is
  how cooperative cancellation of running work reaches the owning worker.
- **Added `Reap`.** Expired running work with no attempts left (or a pending
  cancellation) must not be re-run, so it needs a settling step, or it would
  stay `running` forever. This completes the lease-recovery strategy chosen in
  §26 (claim-time reclaim, plus a reaper for the cases claim must refuse).
- **Added `Requeue`, `Stats`, `Get`, `List`, `Cancel` with an outcome.**
  Required by inspection (§50-52) and metrics gauges (§56).
- **`Retry` or `Release` after a cancel request cancels instead of
  re-queueing.** A cancelled run must never come back.

### 3. Cancellation of running work is cooperative

As the spec says (§52): running work is not killed and is never marked
cancelled while its handler might still run. Added column
`cancel_requested_at`, noticed at the next heartbeat (latency up to
`HeartbeatInterval`), and a defined final state (`completed` if the handler
finished anyway, otherwise `cancelled`; never retried).

### 4. Extra and renamed API names

- `DispatchAt` is a function (§16) and also available as the option `At`
  (Go cannot give one name to both).
- The metadata option is `DispatchMetadata` (`Metadata` is the context type).
- `IdempotencyKey`, `UniquePayload` and `Timeout` are dispatch options. The
  first two map the spec's `idempotency_key` column and "unique-key generation"
  requirement; `Timeout` is §34's per-work timeout.
- Definition forms are `Define` (explicit) and `Declare` (a `Handle` method).
  Defaults on a definition are `DefaultQueue`, `DefaultMaxAttempts`,
  `DefaultPriority`, `DefaultTimeout`, `DefaultBackoff`.
- A package-level `work.SetDefault(rt)` exists next to the context-based
  `work.NewContext(ctx, rt)`. §63 asks for no global mutable registration; the
  default is a *runtime* pointer for the package-level `Dispatch`, not a
  registry, and is optional.

### 5. Per-dispatch backoff is not offered

§13 lists `Backoff` among "potential later options". A backoff policy is code,
which cannot be persisted with a record, so it is configured on the definition
(`DefaultBackoff`) and the worker (`WorkerConfig.Backoff`).

### 6. Uniqueness is scoped per queue and enforced by a column, not a partial index

Lathe's schema builder has no partial indexes and MySQL has none at all.
`active_unique_key` equals `unique_key` while the work is active (available or
running) and is NULL otherwise, under a unique index over
`(queue, active_unique_key)`; NULLs are distinct in all three databases, so
history never blocks dispatch. This needs no dialect-specific DDL and is
expressible in plain Lathe schema terms, so the migrations are generated by
Lathe from `database.Tables()`. Scope is per queue, matching the spec's
"queue + unique_key" sketch. Collation caveat: MySQL's default collation is
case-insensitive, so keys differing only in case collide there.

### 7. Timestamps from the application clock

All scheduling times (available_at, lease_until, ...) are bound parameters from
the `Clock`, in UTC, using Lathe's native timestamp types. This keeps leases
deterministic in tests and portable across dialects; the cost is that nodes
need synchronized clocks (documented). The conformance suite also runs on a
PostgreSQL session set to `Pacific/Auckland` and a MySQL driver location of
`Asia/Tokyo` to prove time zones do not change behavior.

### 8. JSON-only payloads in the database backend

The payload column is JSON (inspectable with ordinary SQL). A serializer
producing non-JSON bytes is refused with `ErrUnsupported`, not silently
base64-wrapped, following §46 (fail explicitly rather than weaken semantics).

### 9. Hand-written Lathe model instead of generated code

`database` uses Lathe's runtime (`Model`, `TableSpec`, typed `Column`s,
transactions, error classification, `Upsert`, `migrate`) but writes the
`TableSpec` by hand rather than running `lathe generate`, because the table
belongs to the library, not to the application's schema. Applications that run
their own codegen can include `database.Tables()` in their schema.

### 10. Extra packages

- `work/backendtest` is public, not `internal/`, so Redis or other backends
  living in other modules can run the conformance suite.
- `work/memory` is an in-memory reference backend. It proves the interface is
  not database-shaped and lets the same conformance suite run twice. It does
  not support transactions and says so through `Capabilities`.
- `work/cli` implements Phase 8 as a library to mount in the application's own
  command (the spec calls for `myapp work ...`), not as a standalone binary.
- Database drivers, examples and the Redis backend live in separate modules
  (`integration/`, `examples/`, `redis/`), so they never become dependencies of
  `work`.

### 11. No OpenTelemetry dependency

§57 asks for tracing hooks. The core defines `Tracer`, `Span` and `Propagator`
interfaces that adapt to OpenTelemetry in a few lines, and
`TracingMiddleware`/trace propagation use them.

## The Redis backend (phase 9)

The spec withholds Redis from v1 until the database backend's conformance tests
are mature (§47-48). They are, so Redis is implemented as `work/redis`.

- **Separate module**, so the core never depends on go-redis.
- **Same contract, same suite.** It passes `backendtest.Run` unchanged, alongside
  the database and memory backends, plus end-to-end worker tests.
- **Lua scripts** make each transition atomic. Ready work is one sorted set per
  (queue, type) with all scores equal, so members sort lexicographically: a
  fixed-width key of inverted priority, available_at and created_at, then the
  id. That reproduces the exact claim order of the SQL backend. Splitting by
  type lets a worker skip types it cannot run without scanning them.
- **Expired leases are reclaimed inside the claim script**, merged with ready
  work in claim order, so a slow-but-alive old owner cannot be racing a new one:
  there is no moment where the work is both queued and running.
- **No transactions** (`Capabilities().Transactions` is false); the spec's
  §46 rule (refuse rather than weaken) applies.
- **Durability is Redis's**: documented, not hidden.
- **`Prune`** exists only here, because Redis keeps every record in memory.
  SQL deployments delete old rows with ordinary SQL on an indexed column.
- Not tested: Redis Cluster and Sentinel topologies (the keys are designed for
  them: one hash tag, one routing key per script), and Redis versions other than
  7.0.

## Declined: RabbitMQ (phase 10)

Not implemented: the spec says "only if real framework users require it. Do not
implement merely because architecture permits." No such requirement exists. The
conformance suite and `Capabilities` are the groundwork if it ever does.

## Decisions the spec left open

- **ID:** UUIDv7 (time-ordered, index friendly, safe to expose), matching
  Lathe's UUID column convention.
- **Reclaim strategy:** claim-time reclaim of expired running work, plus the
  reaper described above. Reclaimed work records `lease expired; reclaimed by
  another worker` in `last_error`.
- **Unknown work types are never claimed** by a worker; an unsupported
  *version* of a known type fails permanently (§76).
- **Status:** `available, running, completed, failed, cancelled` (no
  `retrying`); enforced in the database through Lathe's enum.
- **Indexes:** the spec's claim tuple as written, plus `(status, lease_until)`
  because lease recovery needs it. The spec's separate status and queue
  indexes are covered by the prefixes of those two.
- **Migrations:** kept in their own `work_migrations` table.
- **Worker defaults:** lease 2m, heartbeat lease/3, poll 500ms, shutdown 30s,
  reap 30s, concurrency 10 per queue.

## Known limits

- Tested against PostgreSQL 16, MySQL 8.0, SQLite (mattn/go-sqlite3) and Redis 7.0.
  MariaDB 10.6+ is accepted by the version check but was not run.
- SQLite serializes writers; fine for development and small deployments.
- Claim ordering is `priority DESC, available_at, created_at`; the claim index
  follows the spec's tuple, so very large backlogs with many priorities may
  want an index tuned to your workload. Measure before adding one.
- Cancellation of running work takes up to one heartbeat interval.
